# API Token 余额管理

后台用户管理中的“管理额度”支持追加、扣减、无限制和恢复余额限制。
追加/扣减填写本次调整的数量；不会清空累计用量或按月重置。
每次调整记录操作人、时间、数量和备注；操作 ID 用于防止重复提交。
当前界面展示最近 100 条记录，数据库保留全部记录。

## 数据兼容

V28 新增无限制标记，V29 新增调整流水、请求预占和估算计量标记。
原有 `total_token_quota` 保留为内部累计授予量；用户无需再手工计算它。
可用余额 = 累计授予量 - 累计已用 - 有效预占。
升级不覆盖历史用量、额度、用户或 API Key。
旧的 PUT quota 绝对额度接口返回 410，防止绕过调整流水。
新接口为 POST `/api/admin/api/users/{id}/credits`：

```json
{"operationId":"唯一 UUID", "operation":"add", "amount":5000000, "note":"追加额度"}
```

`operation` 支持 `add`、`deduct`、`unlimited`、`limited`。
无限制期间仍记录消耗；恢复余额限制后继续使用现有余额，不重置历史消耗。
累计已用超过累计授予时，可用余额展示 0，后续追加先抵扣超出部分。

## 请求预占与结算

同一用户的所有 Key 共用一行额度锁。预占时在事务中检查余额，
结算时同样加锁，记录请求和每日用量并删除预占，整个过程在一个事务内完成。
请求 ID 唯一约束防止重复结算。扣减操作不能扣除已被其他请求预占的余额。
调用失败释放预占；流式断开按已经取得的 usage 或已接收文本估算结算。

聊天预占采用请求 JSON 的 UTF-8 字节数作为保守文本输入预算，
加上 max_completion_tokens 或 max_tokens 乘以 n。
用户未指定输出上限时，仅在内部使用 2048 作为输出预占估算，
不会向上游添加任何输出上限字段；输出长度由上游 vLLM 默认配置和剩余上下文决定。
实际输出可能超过内部预占估算，结束后仍按上游返回的实际用量结算。
流式请求强制请求 `stream_options.include_usage=true`。
Embedding/重排使用输入预算；语音预占模型上下文预算，至少 8192。
因此余额不足以覆盖本次预占预算时会提前返回 429；可降低输出上限再试。

上游提供 usage 时以其返回的 Token 数结算；缺失时按文本估算，
在 api_usage_event.estimated 标记为 true。
语音接口不提供 usage 时仅估算识别结果文本，无法得知实际音频输入 Token。
文本估算不等同于模型 tokenizer，图片等多模态输入尤其可能偏离估算。
若实际消耗大于预占，超出部分继续记账并减少后续可用余额。
此机制解决余额被并发重复占用，不承诺任意上游或多模态请求绝对零超额。

预占租期 15 分钟，流式中转每 30 秒随上游数据续期。
进程异常退出后的预占在租期结束后不再占用余额，后续请求清理过期行。
若进程被强杀而上游仍继续计算，最终真实用量无法保证回收，应通过上游日志核账。
前台展示预占数量，避免用户误以为请求尚未结束时余额被永久扣除。

## 验证

ApiCreditRepositoryIntegrationTest 使用 CREDIT_TEST_DB_URL、
CREDIT_TEST_DB_USER、CREDIT_TEST_DB_PASSWORD 连接 PostgreSQL，
每个测试创建独立随机 schema，结束后删除该 schema。
覆盖重复追加、并发预占、幂等结算、超额扣减、无限制切换、过期预占和历史用量保留。
生产升级由 Flyway 自动应用迁移；需发布新版 backend 和 gateway。
